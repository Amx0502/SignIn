# 管理员同班账号二维码并发签到设计

## 目标

管理员在某个课程的二维码签到项中上传一次二维码后，系统自动将同一个二维码 URL 提交给该课程下所有有权限且登录有效的账号，并发执行。普通用户的现有单账号签到行为保持不变。

## 范围与权限

- 仅管理员可以发起批量二维码签到。
- 批量目标限定为 `remote_course_id` 相同的课程账号。
- 目标账号必须处于 `active` 状态并拥有非空 Cookie。
- 管理员可跨用户读取这些目标账号；普通用户不得调用批量能力。
- 每个目标账号使用自己的课程、签到项、表单配置和 Cookie，不能复用发起账号的本地数据库 ID。

## 推荐架构：同步线程池并发

在现有手动签到服务上增加管理员批量入口：

1. 校验 actor 为管理员，并校验上传二维码对应的课程与签到项。
2. 从数据库查找同一 `remote_course_id` 下的 active 账号，并按 `remote_item_id + remote_module` 匹配每个账号自己的签到项。
3. 使用受控线程池并发调用现有 `submit_qr_url` 流程。
4. 每个账号独立生成 `manual` 运行记录，记录账号、课程、签到项、状态和响应摘要。
5. 等待全部任务完成后返回汇总：总数、成功、已签到、失败、未知结果及逐账号明细。

单个账号失败、Cookie 失效或远端响应未知只影响该账号；其他账号继续执行。批量入口不改变原有单账号接口。

## API 与前端行为

- 新增管理员专用批量签到接口，复用现有 `item_id` 和 `qr_url` 请求字段，并返回聚合结果。
- 路由层和服务层双重校验管理员权限。
- 管理员在课程签到中心看到“为同班账号并发签到”操作和结果汇总；普通用户不显示此操作。
- 结果明细可直接刷新运行记录，不要求新增持久化批次表。

## 并发与安全约束

- 使用固定上限的线程池，避免账号数量过多时耗尽线程或连接资源。
- 二维码 URL 仅在本次请求生命周期内使用，不写入长期日志或数据库明文扩散。
- 目标账号查询必须经过管理员作用域；不得因为同课号匹配绕过账号权限。
- 每个线程使用独立请求会话/数据库上下文，避免共享可变表单状态。

## 测试策略

- 服务层测试：非管理员拒绝批量；管理员只选择同课号、active 且有 Cookie 的账号。
- 并发测试：多个目标账号的客户端提交应重叠执行，而非串行执行。
- 结果测试：单个账号异常不阻断其他账号，且每个账号都有独立运行记录与状态。
- 回归测试：现有单账号二维码 URL 校验、课程/签到项匹配和普通用户流程继续通过。
